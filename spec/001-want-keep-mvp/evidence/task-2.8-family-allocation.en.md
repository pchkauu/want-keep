# Task-2.8 — household expense allocation

Implemented the household-expense allocation backend/API. Original base: `cedbe3ba8384071e0e958167d37899ade557c0bc`; branch: `feat/task-2.8-family-allocation`; task-1.6 and task-2.6 are included. The [contract](../contracts.en.md#task-28--household-expense-allocation) retains one household financial fact and an exact member view. No new dependencies; migrations 001–015 and production remain unchanged.

Ledger stores an immutable allocation snapshot by `MembershipID`, independently from payer, account owner and actor. `personal|shared`, exact amount, share and equal modes are supported. Explicit amounts retain their source decimal precision; largest remainder for shares and equal mode uses asset precision with `MembershipID` as stable tie-break. A zero-net item becomes `not_applicable` but retains its basis for a possible later recalculation. Allocation covers items, fallback principal, fees and interest in native assets; internal transfer or exchange principal does not become an expense. Unknown remains unallocated and never turns into zero or 50/50.

`allocation/domain/application` owns merchant/category rules. Conditions in one rule use AND and lower priority wins. Compatible equal-priority rules retain every reference; different outcomes yield `rule_conflict`. Preview performs no write. Every immutable rule revision receives a monotonic number in the household sequence. The first ledger revision captures the current sequence boundary. Late trusted classification of a transaction or item uses only revisions at or before that boundary: a later rule cannot apply even when recorded time is equal or regresses. Explicit purchase and item allocation remain protected. Correcting category, merchant or items re-resolves unprotected parts against that boundary: a matching rule replaces the old result, no rule clears stale shares and returns `unresolved`, and explicit purchase/item inputs remain intact. Source import applies a merchant rule only through a confirmed alias; provider IDs do not substitute for internal merchant/category IDs. Correction, compound decision, selective undo, field protection and source merge use the independent `allocation` field; a source cannot erase the user decision. The review-request hash includes the typed allocation. Matching retains one household and member-effect carrier and makes waiting/non-carrier/internal principal `not_applicable`. The immutable snapshot still retains the purchase and explicit or rule-derived item basis without a member effect; classification refreshes the basis even while waiting, `separate` restores it, and refresh never selects a newer rule revision. Semantically equal decimal values with different scales create no revision. Transaction fallback and all unique item conditions resolve from one batched rule read; allocation snapshots for the whole transaction page are hydrated with a fixed number of set-based queries.

Migration 016 adds rules/revisions/shares, the monotonic household sequence and first-fact rule boundary, immutable transaction/item snapshots with compound household FKs, exact `NUMERIC`, immutable triggers and least-privilege grants. Existing included and excluded expenses receive provable `unresolved`; other operations receive `not_applicable`, with no invented beneficiary. OpenAPI activates transaction allocations and rule CRUD/preview; create and change use separate schemas, so `expectedRevision` is forbidden on create and required on change. Classification-proposal items have a separate schema without a not-yet-accepted allocation snapshot. Go/TypeScript are generated from one source. Mutation routes use the session actor, Origin/CSRF, idempotency, expected revision and command recovery; a missing, foreign or archived condition returns safe `404 not_found`, never an internal error.

## Verification matrix

Required commands: `make check`; `make test-integration AREA=all`; `make test-family-allocation-race`; affected race suites; `make test-integration AREA=privacy`; `git diff --check`. PostgreSQL 17.11 is digest-pinned; missing DB fails the suite. Family-allocation integration/race are included in CI. Exact results for the published candidate are recorded in the PR and Issue.

The suite checks RUB, USD, USDT, USDC, BTC and ETH at arbitrary precision; 50/50, 60/40, explicit amounts `1 = 0.5 + 0.5`, deterministic remainder and mixed receipt `1000 → A 400 + B 600`. It covers item overrides, a fully unresolved item split whose explicit reason survives correction/matching refresh, preservation of a rule-derived item basis and exact revision, share-based and amount-based purchase-fallback recalculation without promoting derived item snapshots to explicit overrides, a third-asset fee and repeated `MembershipID` inputs across native assets. Rule precedence/conflict/preview, persisted `rule_conflict` for manual and imported facts, the rule boundary for late transaction and item classification with equal or regressed time, explicit-item preservation while another item resolves, semantic decimal no-change, replacement of an earlier rule after classification correction, clearing stale shares when no rule matches, basis refresh while matching waits, exclusion of later rules, explicit-allocation protection, and rule archival after its merchant/category is archived are also covered. HTTP regressions enforce `expectedRevision` only on change and identical `404` responses for missing, foreign and archived conditions. Confirmed merchant aliases without trusting provider IDs, ignored allocation from provider payloads, `not_applicable` imported income and rule allocation of only a transfer's expense fee are verified together with correction/undo/source protection, the complete review hash, one effect across matching evidence and restoration of a retained allocation basis after waiting → separate across a PostgreSQL restart.

PostgreSQL scenarios verify concurrent revisions by both members, replay, rollback, lost response after commit, household isolation, session-bound cursor, CSRF, command visibility, migration-over-015, immutable history and unprivileged-role grants. Allocation changes neither postings nor account projections.
