# Task-7.1: desktop-вход и начало учёта

[English](task-7.1-access.en.md) · [Issue #48](https://github.com/pchkauu/want-keep/issues/48) · [Навигация](../navigation.md)

## Реализация

React Router Data Mode управляет оболочкой и маршрутами SCR-001–005. Модули identity и accounts владеют своими состояниями и HTTP-преобразованиями; дизайн-система получает presentation props. Единственная новая runtime-зависимость — react-router 8.3.1. Backend, OpenAPI, миграции и production не менялись.

Работают закрытый bootstrap, native WebAuthn, вход двух участников, личное восстановление, preview/принятие приглашения и выдача/перевыпуск/отзыв приглашения в onboarding. Минимальный `/settings/security` перевыпускает recovery-коды после собственного свежего подтверждения. Коды показываются один раз и очищаются при утрате доступа; копирование/скачивание выполняются явно. При неизвестном ответе enrollment сначала проверяется `/me`, затем предлагается вход новым ключом. Завершение не повторяется автоматически.

CSRF хранится в памяти, сессия — в защищённой cookie. Пределы 12 часов/30 минут проверяются сервером и закрывают клиентское представление; пользовательская активность сигнализируется только в видимой вкладке не чаще раза в минуту. Фоновые чтения не продлевают простой. Старые ответы отбрасываются при изменении сессии. При logout с потерянным ответом доступ скрывается без заявления об отзыве серверной сессии. Между вкладками передаётся только сигнал перепроверки.

Onboarding создаёт настоящий наличный счёт task-2.1: актив, принадлежность, календарная дата и точный начальный остаток. UUID создаётся до POST. Timeout и `not_found` не разрешают новый ключ; явный повтор сохраняет ключ и payload. После reload проверяются recent commands. Подтверждение требует результата команды и чтения счёта; список обновляется после создания. Суммы не проходят через Number. При смене участника финансовый черновик очищается, после expiry сохраняется только в памяти для того же участника.

Обзор показывает доступные счета и следующие действия. Остальные финансовые разделы имеют состояние недоступности. Язык выбирается в порядке browser preference → подтверждённый профиль → поддерживаемый browser locale → RU; только язык сохраняется в localStorage. Формы и церемония переживают переключение RU/EN. Приглашение из fragment удаляется из адреса до рендера; секреты не записываются в URL или постоянное хранилище.

При локальном expiry вход сначала перечитывает /me: живая общая cookie восстанавливает сессию без нового prompt и без продления простоя. Pending-команда допускает явный replay исходного запроса. После reload пользователь может восстановить поля с прежним ключом; сервер проверяет hash и отклоняет любое отличие без эффекта.

## Проверки

`make e2e SCENARIO=access` поднимает отдельные PostgreSQL 17.11 и настоящий Go API, применяет миграции и создаёт закрытый тестовый bootstrap. Chromium использует разные виртуальные аутентификаторы. Отсутствие инфраструктуры завершает проверку ошибкой. API успешных сценариев не подменяется; потеря ответа моделируется после реального commit. Trace с секретами отключён. Новая CI job выполняет этот сценарий.

`make check` прошёл: форматирование, lint, TypeScript, 104 web unit-тестов, Go/collector, build, SDD и воспроизводимость OpenAPI. Профиль identity — 15 тестов, accounts — 13. Access E2E прошёл полный реальный семейный сценарий, потерю ответов bootstrap/приглашения/счёта, отказ чужому Origin/RP и скрытие формы по клиентскому idle expiry. Общий `make e2e SCENARIO=all` прошёл 27 сценариев через соответствующие launcher. Реальный сбой записи PostgreSQL после durable-регистрации команды подтверждает повтор с тем же ключом, reload/восстановление полей, отказ изменённому payload и один итоговый счёт. Истечение часов вкладки при живой серверной cookie восстанавливает черновик того же участника. Дизайн-регрессии: 7 token и 19 component сценариев. PostgreSQL identity/household/accounts suites прошли. `git diff --check` прошёл. Build сообщает предупреждение о размере главного chunk; установленного блокирующего лимита размера нет. Настоящий Chrome на macOS проверен при 1414×943 CSS px / 100% и 707×472 / 200%, затем возвращён к 100%. Пользователь подтвердил native-создание passkey и последующий вход. Ручная проверка включает системное создание passkey с участием пользователя, RU/EN, точный наличный остаток, навигацию и масштаб 100%/200%. Автоматические контрольные области — 1280×720, 1440×900 и 640×360/720×450 для увеличенного содержимого. Это не доказательство физических размеров окна Chrome.
