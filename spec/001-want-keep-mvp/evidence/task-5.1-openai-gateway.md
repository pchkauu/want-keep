# task-5.1 — OpenAI gateway и контроль расходов

[English](task-5.1-openai-gateway.en.md)

## Результат и границы

Реализованы gateway Responses API, точный семейный лимит $50 за UTC-месяц, долговечные AI-попытки, интеграция с worker и операторская сверка неизвестной оплаты. Выбранный `gpt-5.6-terra` с `reasoning.effort=xhigh` материализуется из `terra_xhigh` в проверяемый runtime-contract. Исторический результат 206/206 подтверждает только исходную синтетическую квалификацию: runtime-добавления USDC и pseudonymous case envelope проверены локально и блокируют production до отдельной live-квалификации. Локальные и CI-тесты используют поддельный HTTP transport; реальный OpenAI API и production не вызывались.

Task-5.1 сохраняет результат модели со статусом `pending_validation`. Он не изменяет финансовый журнал: проверка полномочий и применение предложения остаются task-5.2, разбор чеков — task-5.3, инсайты — task-5.5. Публичный OpenAPI не изменён.

## Исполняемый контракт

- `ai/domain` хранит точные decimal USD, usage с различием отсутствующего и нулевого `cache_write_tokens`, тариф `$2/$0.20/$2.50/$12` и состояния попытки. Reservation включает `counted input + 32`, максимальный output и консервативный cache-write. Reasoning входит в output один раз.
- `gateways/openai` закрепляет `openai-go/v3` v3.56.0, отключает SDK retries и отправляет только согласованные поля Input Tokens и Responses API. Generation всегда foreground, `store=false`, default service tier, explicit cache, disabled truncation и parallel tools. API key читается только из приватного абсолютного файла.
- `scripts/generate-openai-runtime.py` создаёт runtime-contract из `evidence/openai.prompts.json`; `make check-ai-runtime-contract` сравнивает генерацию во временном файле и запрещает drift prompt/schema/config. Source qualification fingerprint и runtime schema fingerprint различаются явно. Runtime input использует ровно один pseudonymous qualified-case для ledger revision; runtime schema поддерживает RUB, USD, USDT, USDC, BTC и ETH. Это локально проверенная совместимость; `production_admitted=false` запрещает реальный запуск до нового live eval.
- Миграция 016 хранит неизменяемую identity попытки и append-only состояния с request/prompt/schema/config fingerprints, разрешённым input, provider ID, возвращённой моделью, доверенным usage, отдельным ограниченным наблюдением всех присутствовавших числовых usage-полей, месяцем резерва, резервом, стоимостью, output и сверкой. Decimal-поля стоимости ограничены тем же пределом 128 символов при обычной записи и maintenance-сверке. Application role имеет SELECT/INSERT без UPDATE/DELETE. Maintenance role не имеет прямого доступа к таблицам AI/jobs и исполняет только ограниченную `SECURITY DEFINER`-операцию сверки.
- Перед платным вызовом storage под household lock проверяет глобальный unresolved-barrier, сумму `actual + reserved + unknown`, два слота и месячный лимит. Те же ограничения проверяются после Input Tokens ответа, перед резервом и непосредственно перед сохранением external-started marker. Финальная проверка включает резервы, уже созданные в том же UTC-месяце; переход через UTC-границу переносит текущий резерв только после проверки лимита нового месяца. Нулевой/отсутствующий count запрещён. Provider IO не выполняется в транзакции.
- После generation структурированные 429 `rate_limit_exceeded` и `insufficient_quota` считаются подтверждёнными отказами без списания: только `rate_limit_exceeded` допускает одну новую оплачиваемую попытку с `Retry-After`, ограниченным пятью минутами; следующий такой отказ завершает job постоянной ошибкой. `insufficient_quota` завершает попытку без повтора, а неизвестный класс 429 остаётся `unknown`. Input counting, pre-generation outage и восстановленный резерв без external-started marker не расходуют лимит generation-попыток; повторные безопасные lease-recovery возвращают generic attempt до вызова provider, а неотправленная job отозванного участника завершается без возврата в очередь. Повтор до generation переводит job в `gateway_unavailable`, сохраняет backoff до пяти минут и исходный 24-часовой deadline; 401/403 на Input Tokens остаются восстановимой ошибкой конфигурации. Любой иной результат после marker без доказательства отсутствия списания, включая 400/401/403, 408/5xx, таймаут и неопределённый transport outcome, становится `unknown`, сохраняет provider observation, резерв и job `unresolved`. Unknown outcome продолжает учитываться по полному резерву, даже если наблюдаемые счётчики выглядят внутренне согласованными; фактическую стоимость устанавливает только сверка. Для известного результата input usage принимается только в диапазоне от подсчитанного значения до `count + 32`, output — от 1 до route cap. Отсутствующий/противоречивый usage, пропуск обязательного nullable-поля strict output или несовпадающая provider model переводятся в безопасное ошибочное состояние; наблюдаемые счётчики сохраняются как evidence, но не участвуют в расчёте стоимости. Отсутствующий `cache_write_tokens` создаёт консервативную известную стоимость: она учитывается в бюджете, не закрывает семейный gateway и может быть позже заменена точной стоимостью через operator reconciliation. Новый месяц, смена ключа или проекта не снимают unknown barrier. Оператор подтверждает точную стоимость либо отсутствие списания по request ID и безопасной структурной evidence-ссылке; живой lease нельзя сверить. Точный повтор уже подтверждённой сверки идемпотентен, а иная стоимость или evidence-ссылка отклоняется. Сверка известного terminal outcome при превышении резерва или консервативной стоимости сохраняет outcome/output/validation и не возобновляет job. Сверка сериализуется с резервированием по блокировке семьи. Доверенный resumer возвращает budget-waiting job в `ready`, когда сохранённый резерв снова помещается в лимит либо начинается новый UTC-месяц; повторяющийся gateway-resumer выбирает только готовые по backoff ограниченные пакеты после восстановления provider и завершает истёкшее ожидание с `deadline_exceeded`. Финальная проверка резерва остаётся атомарной.
- Любой известный provider outcome и соответствующий terminal/retry job-state сохраняются атомарно. Для успеха в той же транзакции записываются usage, output, `pending_validation` и job receipt. Ошибка job transition откатывает settlement целиком. Recovery/cancellation завершает только counting/reserved попытки, которые точно не дошли до provider; external-started остаётся unresolved. Повтор worker после commit не вызывает provider снова. Проекция в OpenAI ограничена конкретной ledger revision, заменяет внутренние ID стабильными локальными pseudonyms и исключает credentials, sessions, raw source payloads и данные других семей.

## Эксплуатационная передача

Worker использует `WANT_KEEP_OPENAI_API_KEY_FILE`. При корректном gateway отдельный повторяющийся resumer возвращает все `gateway_unavailable` задания в `ready` ограниченными пакетами; ошибка конфигурации пишет только безопасный код, оставляет AI в ожидании и не останавливает sync, outbox или scheduler. Необязательные `WANT_KEEP_OPENAI_PROJECT_ID` и test/development `WANT_KEEP_OPENAI_BASE_URL` не меняют семейный учёт. Production запрещает custom base URL и текущий runtime-контракт до новой live-квалификации. Сверка запускается maintenance DSN через `go run ./cmd/ai-reconcile --request-id ... --outcome charged|not_charged --actual-usd ... --evidence-ref ...`; для `charged` требуется положительная точная стоимость, plaintext key и финансовый текст в параметры не передаются.

OpenAI может хранить abuse-monitoring данные до 30 дней по действующим API data controls. `store=false` отключает обычное application-state хранение ответа, но не отменяет эту политику. Перед production task-8.1 проверяет secret provisioning, egress, тарифы, retention и operational runbook. Live-вызов требует отдельного разрешения и расхода.

SDD остаётся **Ready for development**. Task-5.1 не подтверждает готовность task-5.2, UI или production.
