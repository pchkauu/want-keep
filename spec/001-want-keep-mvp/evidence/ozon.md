[English](ozon.en.md)

Статус: **research завершён; structured responses получены, автоматический connector не реализован**. ## Структурированный контракт из HAR

OZON-E17 — предоставленная владельцем запись: 291 запрос, 290 тел ответа. OZON-E18 — дополнительная запись пагинации: 28 запросов. Все записанные HTTP-ответы имеют код 200; это не проверка поведения при 401/403/429. Исходники хранятся локально вне Git. Их SHA-256, индексы запросов и [проекции ответов с синтетическими значениями](ozon.samples.json) позволяют сверить происхождение образцов. Публикуемые JSON сохраняют только выбранные поля; это не полные ответы и не данные авторизации.

### Маршруты чтения

Все пять маршрутов наблюдались на `https://finance.ozon.ru`, метод **POST**, JSON request/response. Это внутренний интерфейс веб-кабинета, а не подтверждённый публичный retail API. Публикация адреса не означает право на платёж или доказанную возможность автономного серверного вызова.

| Маршрут | Запрос | Поля ответа и образец |
| --- | --- | --- |
| `/apps/pfm/api/operations/modalAccounts` | `{}` | `data.me.client.accounts[]`: accountNumber, accountToken, balance, productTypeV2/V3, status; `mainAccount.accountToken`. OZON-S01 |
| `/api/v4/cards/all` | `{}` | `data.me.client.cards[]`: accountNumberV2, cardId, cardMode, status, product. OZON-S02 |
| `/api/v4/userBalance` | `{}` | `data.ozonUser.balance.cents`. OZON-S03 |
| `/apps/pfm/api/operations/groupOperationsV3` | `filter`, `cursorPagination: {cursor, perPage}` | `data.me.client.groupOperationsV3`: items, cursors.next/prev. OZON-S07–S10 |
| `/apps/pfm/api/operations/operationById` | `{id, timeZone}`; id соответствует lastOperationId | `data.me.client.groupOperationsV3.items[]`; детали дополнительно содержат accountNumber и direction. OZON-S04–S06 |

Структура фильтра: `effect="EFFECT_UNKNOWN"`, `coopAccountIDs=[]`, `accountTokens=[]`, `pfmTags=[]`, `timeZone="Europe/Moscow"`. Исторический запрос дополнительно передал `dateRange={from:"2026-08-01",to:"2026-08-31"}`. Непустые фильтры счёта/категорий не проверялись. Параметр `perPage=30` наблюдался, но это не доказанный максимум API.

Только эти проверенные операции чтения являются кандидатами для финансового allowlist. Нельзя разрешать весь `/api/`, все POST или все запросы страницы: в записи есть фоновые `/apps/promo/api/banners/setAction`, прогрев кеша, контексты, реклама и другие несвязанные маршруты. UI-навигация не доказывает исполнение allowlist будущим сборщиком. Cookie/session и непрозрачные ссылки остаются внутри защищённого адаптера, не передаются AI.

### Идентичность и точные суммы

| Поле | Подтверждено | Правило адаптера |
| --- | --- | --- |
| accountNumber / accountNumberV2 | Номер из modalAccounts совпал с номером карты и трёх деталей операций; UI-номер совпал после нового входа (OZON-E16) | Связать карту со счётом, не создавать второй баланс. Окончательный namespace включает provider и подтверждённую идентичность счёта, а не connectionId или автора действия |
| accountToken | В одном HAR пять разных значений для того же подтверждённого номера счёта | Непрозрачная ссылка контекста, не устойчивый ID; не включать в финансовый fingerprint. Не декодировать и не публиковать исходное значение. Для строки списка подтвердить счёт через детали, если иного проверенного mapping нет |
| lastOperationId | 210 разных значений в семи страницах OZON-E18; запрос деталей использует именно этот ID | Кандидат source ID внутри подтверждённого namespace счёта. Повтор ID не создаёт второй факт; изменения финансовых полей требуют revision. Смена ID при будущем lifecycle ещё требует сверки |
| groupID | В 210 строках 209 разных groupID: перевод и комиссия имеют общий groupID, но разные lastOperationId | Не использовать groupID как единственный ключ дедупликации. Сохранять для связывания и расследования изменений |
| accountAmount / originalAmount | `{amountAbs:{cents:integer,currencyName:"RUR"},sign:"POSITIVE"\|"NEGATIVE"}` | RUR → RUB на границе; целые копейки → точная десятичная сумма /100 с отдельным знаком. Не использовать float или UI-агрегаты |
| balance | modalAccounts.balance совпал с userBalance.cents в наблюдаемом снимке; нет отдельных owned/available/locked | Сохранить сообщённый баланс и его происхождение. Не объявлять всю сумму доступной для дневных лимитов и не подставлять 0 для отсутствующего hold |
| time / lastOperationTime | Timestamp-строки с `Z`; запрос передаёт Europe/Moscow | Сохранять время источника и отдельно fetchedAt. Различие cash/booking/value date не выводить из имени поля; для неподтверждённого календарного смысла сохранять ограничение |

Совпадение номера между двумя входами проверено для одного владельца. Второй независимый внешний аккаунт не подключался. Проверка изоляции двух владельцев, lease/version и восстановления импортера остаётся обязательной; один HAR не является её результатом.

### Статусы, возвраты и комиссии

- В OZON-E18: 206 строк `GROUP_OPERATION_CONFIRMED`, 4 `GROUP_OPERATION_CANCELED`. Отменённая строка может сохранять отрицательную сумму; её нельзя учитывать как подтверждённый расход. Неизвестный статус не становится posted.
- `groupOperationType="OZON"` встречается у покупки и возврата. `meta.__typename` различает `OzonClearingOperationMeta` и `OzonRefundOperationMeta`; одного знака или merchant name недостаточно для экономического типа.
- `AUTHORIZATION` встречается с `ClearingOperationMeta` и с `AuthorizationOperationMeta`. Нельзя классифицировать жизненный цикл только по groupOperationType. Неизвестное сочетание status/type/meta требует явного разбора, а не автопроводки.
- В OZON-S10 комиссия `TRANSFER_BY_CARD_NUMBER_COMMISSION` имеет собственный lastOperationId и `parentOperationId`, равный lastOperationId связанного `TRANSFER_BY_CARD_NUMBER_OUTGOING`. Обе суммы отрицательные, у комиссии `meta=null`; это допустимый наблюдаемый вариант. Обе записи сохраняются раздельно, комиссия не добавляется ещё раз из текста/расчёта. Обобщение net/gross на другие виды комиссий не проверено.
- В прочитанном возврате Ozon `parentOperationId=null`. Исходную покупку нельзя считать установленной по одному названию или общему типу. Сопоставление чека/покупки либо уточнение пользователя выполняет существующий процесс Want Keep; только подтверждённая связь пересчитывает исходный месяц.
- `INTERNAL_TRANSFER_*` — название типа у провайдера, а не доказательство перевода между собственными семейными счетами. Семейный перевод подтверждается идентичностью обеих сторон.

### Пагинация и границы доказательства

OZON-E18 содержит семь последовательных страниц по 30 строк. Каждый следующий request.cursor точно совпал с response.cursors.next предыдущей страницы; фильтр сохранён. Межстраничных повторов groupID не было, но внутри одной страницы есть описанная пара перевод/комиссия. Все 210 lastOperationId различны. Во всех семи ответах next непустой: **конец истории не достигнут**. Отсутствие дальнейших запросов в HAR не означает конец данных.

В OZON-E17 три повторных первых страницы имели одинаковые проверенные финансовые поля и ID. Все 30 строк августовского запроса попали в указанный диапазон по Europe/Moscow; есть запись последнего дня. Первый день, завершение диапазона, retention и восстановление после ошибки пока не доказаны. Проверка возраста самого раннего отображённого дня не заменяет retention contract.

Сборщик должен продвигать курсор только после устойчивого сохранения страницы, повторять прерванную страницу без второго эффекта и хранить coverage с фильтром и границами. Эти правила — требования будущей реализации, не выполненные runtime-тесты. Запрошен отдельный HAR до конца августовского диапазона.

### Сессия и оставшиеся вопросы

UI потребовал повторный вход (OZON-E15), владелец восстановил доступ (OZON-E16). В HAR также наблюдается `POST /api/v4/auth/check` → `data.authV2.bankAuth.tokenExpiresAfter`. Изменение счётчика соответствует примерно 1000 единицам за секунду между двумя парами наблюдений; миллисекунды — вывод из измерения, не опубликованная гарантия. Полная длительность сессии, поддерживаемый refresh и автономная почасовая работа не проверены. Не создавать фиктивный refresh endpoint и не обходить требование входа владельца.

Прямой повтор HTTP-вызовов отдельным сборщиком, серверные ограничения частоты, ошибки авторизации, два внешних аккаунта и поздние изменения не тестировались. В текущем HAR нет исходных заголовков авторизации; он задаёт форму чтения, но не является переносимой банковской сессией.

**Итог research:** реальные routes/fields, 10 synthetic projections и RU/EN matrix подготовлены. Issue #3 означает готовность отчёта, не автоматической интеграции. OZON-B02/B04/B05 стали runtime gates task-4.3 по решению task-0.10; SDD Ready и provider acceptance различаются.

## Безопасность и воспроизведение

Исследование ограничено чтением. Платежи, переводы денег, выпуск/активация карт и изменение продуктов не выполнялись. Вход и MFA выполняет владелец в Chrome. Чтение реквизитов для сравнения ID отдельно разрешено владельцем; значения не публикуются. Банковская сессия имеет более широкие права, чем будущий сборщик, поэтому исполнение allowlist требуется проверить в реализации.

Владелец экспортирует Network → **Save all [listed] as HAR (sanitized)** после обычного просмотра. Как описано в [документации Chrome](https://developer.chrome.com/docs/devtools/network/reference/#save-as-har), исключение стандартных чувствительных заголовков не удаляет все персональные значения из URL и тел. Исходные HAR остаются в локальном `tmp/ozon-read-contract/`, каталог доступен только владельцу; Git исключает `tmp/` и `*.har`. Не переносить HAR, cookies или контексты сессии в Issue.

Публичные OZON-S01–S10 сохраняют выбранные исходные имена/типы полей и связи. Имена, суммы, даты, номера, ID и непрозрачные ссылки заменены синтетическими значениями; форма настоящего номера счёта намеренно не воспроизводится. Поля вне проекции исключены. Образцы предназначены для проектирования и будущих contract-тестов, не для авторизации или вызова банка.
