# Task-7.9: семейный контекст в desktop-интерфейсе

[English](task-7.9-household-context.en.md) · [Issue #56](https://github.com/pchkauu/want-keep/issues/56) · [Навигация](../navigation.md)

## Реализация

Публичный модуль `web/src/features/household/` владеет транспортным преобразованием `/household` и приглашений, состоянием загрузки и выбранным представлением. Контроллер связывает ответ с household, user и session; любая смена session ID начинает новую загрузку, поздний ответ прежней сессии отбрасывается. Reauthentication того же участника не размонтирует текущий экран, но повторно проверяет семейное состояние. Identity сохраняет WebAuthn и принятие приглашения; accounts получает только типизированный household view и список участников.

Разрез хранится в URL как `?view=household` или `?view=member&member=<userId>`. Неизвестный, отсутствующий или pending member заменяется семейным видом. Переходы shell переносят только view/member. Для будущих отчётов модуль предоставляет точную форму `{view}` или `{view, memberId}` существующего OpenAPI. Вошедший участник остаётся отдельной подписью; переключение не меняет session principal.

`/settings/household` показывает состав, статус членств, лимит, timezone, актуальное приглашение, границы личных и семейных ресурсов и ссылку на собственную безопасность. Выдача и перевыпуск требуют личной reauthentication, отзыв использует действующую сессию. Потерянный ответ и конфликт revision требуют перечитать метаданные; секретная ссылка не воспроизводится. Offline блокирует изменения, сохраняя доступное чтение. Смена ролей, выход/замена участника и восстановление через партнёра отсутствуют.

Список счетов сохраняет server-returned ownership и external account owner. Семейный вид группирует все счета; индивидуальный показывает семейные и личные счета выбранного участника. Подписи различают «семейный», «личный · имя» и владельца платформы. Скрытые строки явно остаются частью семейного денежного пула. Создание личного наличного счёта по-прежнему получает owner из `CashController.userId`, созданного для вошедшего actor; URL-фильтр не передаётся в mutation.

Backend, OpenAPI, миграции, зависимости и production не изменялись.

## Проверки

`make test-web FILTER=household` проверяет URL-нормализацию, форму report context, inactive/unknown member, смену сессии и поздний ответ, transport membership/revision, семейную фильтрацию счетов и независимость actor от выбранного разреза.

`make e2e SCENARIO=family-access` поднимает отдельные PostgreSQL 17.11 и Go API, применяет миграции и использует два виртуальных WebAuthn-аутентификатора. Сценарий проходит bootstrap, личный и семейный наличные счета, потерю ответа приглашения, stale revision, отзыв и отказ отозванному токену, присоединение партнёра, оба `/settings/household`, deep link/back/forward, возврат из незавершённого раздела, безопасный семейный вид при отказе `/household`, группировку счетов и создание личного счёта партнёром при выбранном Андрее. Проверяются RU/EN, клавиатура, reduced motion, 1280×720, 1440×900 и эквиваленты 200% 640×360/720×450 без горизонтального переполнения.

`make check` прошёл: форматирование, lint, TypeScript, 117 web unit-тестов, Go/collector, build, SDD и воспроизводимость OpenAPI. Профиль `make test-web FILTER=household` содержит 10 тестов. `make e2e SCENARIO=all` прошёл 28 сценариев: access, 19 component, 7 token и family-access. PostgreSQL household/accounts integration и обе race suites прошли на отдельной базе. `git diff --check` прошёл.

Настоящий Chrome на macOS проверен при 1414×943 CSS px / 100% и 707×471 / 200%, затем возвращён к 100%. Пользователь подтвердил native-создание passkey. Проверены семейный переключатель, отдельная подпись actor, `/settings/household`, сохранение view в ссылке личной безопасности, прокрутка действий и отсутствие горизонтального переполнения. После dev-only HMR словаря выполнен чистый reload; текущих console errors нет. Автоматические контрольные области 1280×720, 1440×900 и 640×360/720×450 проверяют полный сценарий с двумя участниками. Это не доказательство физических размеров окна Chrome.

Self review, CI опубликованного SHA и merge фиксируются отдельно в PR и issue.
