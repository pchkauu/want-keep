## Маршруты и контракт чтения

Это **UI-маршруты**, не HTTP API endpoints. Сетевые методы/schema и raw responses кабинета не получены; опубликованный внешний API рассмотрен отдельно ниже. Документированный интерфейс инструмента Chrome предоставляет DOM/действия, но не перехват сетевых requests/responses; скрытое состояние приложения не извлекалось.

| UI / действие | Наблюдаемый результат | Ограничение |
| --- | --- | --- |
| /dashboard, ссылка /dashboard/ | Продукты и общий баланс | Общий баланс не означает доступные семейные средства |
| Карточка текущего/накопительного счёта → /accounts/{account-reference} | Остаток, история, маска счёта, действия/сведения | Reference текущего счёта — 20 цифр в URL; это приватный идентификатор, значение не публикуется; реквизиты отдельно не открывались |
| Карточка вклада → /deposits/{deposit-reference} | Остаток, сроки, доход, график/история | Приватный reference не равен доказанной identity между сессиями |
| Строка операции → диалог | Точная сумма, тип/описание, дата/время, доступные детали и иногда явный статус | На проверенной выплате URL остался маршрутом вклада; отдельного operation ID в диалоге не установлено |
| /history/ → календарь | Выбранный диапазон и история | Выбор дат не добавил query к этому UI URL; URL сам по себе не воспроизводит фильтр |
| /marketplace/ → ожидаемое начисление → /profit/cashback | Баланс, ожидание, месячная сводка; query loyaltyType/month | Значения query не являются банковскими transaction IDs |
| «Вся история» → /partner-offers/accruals-history | Типы начислений, валюты, даты, строки кэшбэка; query currencies/groups/limit/from/to | limit в UI URL не доказывает server page size; RUR требует явного boundary mapping к RUB после подтверждения schema |
| Строка кэшбэка → диалог | Будущая дата начисления, дата/сумма покупки, категория и маска карты | Нет доказанной общей identity с банковской покупкой/выплатой |

SourceRecord должен следовать [общему контракту](../contracts.md): household/provider/stable external account/product/log namespace, source ID либо доказанная identity strategy, revision и provenance. Ни connectionId, ни маска карты, ни название/сумма/время, ни порядок строк не доказывают уникальность. Атрибут data-test-id=operation-cell в ALFA-E13 обозначает UI-компонент, а не уникальную запись. Пока identity не закрыта, нельзя выдавать повторное DOM-чтение за идемпотентность импорта.

### Синтетические API-примеры и mapping

Следующие значения вымышлены. Это минимальные образцы по опубликованной форме, **не успешные requests/responses и не полный schema fixture**; account-example обозначает заглушку, которую нельзя отправлять в банк.

~~~http
GET /api/pp/v1/accounts/account-example
Accept: application/json
~~~

~~~json
{"mnemonic":"Example","number":"account-example","type":"EE","status":"ACTIVE","dateCreated":"2026-01-01","balance":{"currency":"RUR","minorUnits":100,"holds":2500,"amount":125000}}
~~~

~~~http
GET /api/pp/v1/operations/operation-example
Accept: application/json
~~~

~~~json
{"id":"operation-example","dateTime":"2026-08-15T09:30:00Z","title":"Example shop","amount":{"value":125040,"currency":"RUR","minorUnits":100},"direction":"EXPENSE","status":"HOLD","fee":0,"isAnotherClient":false,"cashout":false}
~~~

Заголовок авторизации намеренно отсутствует. Для Want Keep предлагается сохранять строковые provider IDs без преобразования в float; amount.value=125040 при подтверждённом масштабе 100 даёт 1250.40 RUB. RUR→RUB — явный mapping на границе, исходный код сохраняется. До уточнения семантики нельзя повторно вычитать holds или прибавлять fee. Статус null/неизвестный enum сохраняет неопределённость. INCOME не превращает внутренний перевод в доход; HOLD не создаёт окончательный posted-факт. Это ограничения будущего mapping, а не реализованный код.

### Решение по автоматизации и восстановлению

Предпочтителен официальный API **после** подтверждения доступа к нужным продуктам. Для browser-варианта подтверждено только интерактивное чтение указанных UI; контракт фонового Playwright-сборщика остаётся открытым. Скрейпинг текстов суммы/имени/времени не решает устойчивую identity финансового журнала.

Будущий allowlist должен перечислять origin, HTTP method, path, query/body и ответ для конкретного чтения. Scope сам по себе не заменяет allowlist. Карточные действия, платежи, изменение лимитов, открытие/закрытие продукта и начисление кэшбэка исключаются. POST запроса истории лояльности рассматривается отдельно от POST финансового действия; заказы документов отдельно проверяются на стоимость, побочные эффекты и неизвестный результат перед повтором.

План проверки task-4.1 после разрешения доступа: фиксированный диапазон/размер страницы; persist страницы до продвижения offset; overlap/replay и повторное чтение изменившихся операций; сравнение с источником и восстановление после сбоя второй страницы. Offset-пагинация не гарантирует отсутствие пропусков при изменениях в начале списка. До подтверждения поведения нельзя заявлять полную историю. При 401 источник ждёт восстановления доступа владельцем; при 403 показывает недоступный scope; 429/5xx дают ограниченные повторы с backoff. Численные квоты и срок refresh/session не получены; часовая синхронизация — требование Want Keep, не обещание банка.

### Что требуется от владельца и банка

Для закрытия ALFA-B02 банк должен подтвердить возможность личного пилота без обязательных платных внешних источников, доступные scopes/продукты, лимиты и порядок выдачи тестового/промышленного доступа. Владелец предоставляет доступ безопасно, вне Git/чата. При выборе browser-сборщика нужен разрешённый способ получить структурированный read-контракт и идентификаторы, а не экспорт сессии в переписку. Письма банку и договоры в этом исследовании не отправлялись и не подписывались.

Для ALFA-B03 нужны второй независимый внешний аккаунт и сравнение тех же сущностей после reauth; для ALFA-B04 — разрешённый кредитный образец либо явное решение владельца об изменении scope. Для ALFA-B05/B06 — уточнение схем условий, fee/status и связи начисление–выплата–коррекция. Эти пункты нельзя закрыть синтетическим ответом или отсутствием соответствующего продукта у текущего владельца.

## Семантика денег и условий

- В покупке виден pending-текст, во внутреннем переводе — «Операция выполнена». В прочитанной выплате процентов явный статус отсутствовал. Raw enum и occurredAt/postedAt/timezone не подтверждены; отсутствие pending-текста не означает posted. UI-статус является свидетельством, но mapping требует проверенного контракта.
- Вклад тоже помечает остаток словом «Доступно», хотя пополнение/частичное снятие в обоих просмотренных образцах запрещены. Такой остаток нельзя автоматически включать в расходный пул; term/lock и условия снятия принадлежат финансовому домену.
- Вклады показывают полученный доход, будущую выплату, доход за весь срок и график с прошлыми/будущими датами. История отдельно показывает выплаты и открытие депозита. Пополнение при открытии — движение капитала; выплата и та же строка графика не создают два дохода. «Дата закрытия» и «Дата продления» различаются; в просмотренных образцах автопродление соответственно выключено/включено.
- В «О вкладе» структурированы начальная сумма, срок, даты, годовая ставка, капитализация, счёт возврата/выплаты и ограничения. Тексты выплаты на вклад и счёта возврата не определяют весь алгоритм расчёта/погашения. Day-count, округление, досрочное закрытие, история условий и точное назначение всех ставок ещё нужны.
- «О накопительном счёте» содержит FAQ: ежедневный остаток на начало дня, выплата в конце месяца, возможные изменения ставки/надбавок, отсутствие процентов за месяц при досрочном закрытии. Это источник текста, а не исполнимый договор. Персональная eligibility, полная история ставок, расчётная база и округление не проверены; AI не превращает FAQ в гарантированную модель.
- Внутренний перевод в UI исключён из банковской аналитики. В его деталях показан счёт списания, но счёт зачисления не установлен. Want Keep подтверждает собственность и обе стороны отдельно; имя или банковская категория не доказывают принадлежность семейному пулу.
- Кэшбэк у покупки и в истории начислений может ожидать выплаты. В истории накопительного счёта найден отдельный кредитующий платёж. Ожидаемое начисление не увеличивает доступный бюджет; выплата учитывается один раз после подтверждения статуса и связи с начислением. Политика классификации cashback/реверсивной компенсации требует отдельного решения доменного контракта: название не делает любое зачисление обычным доходом или возвратом.
- В просмотренных деталях не установлены отдельные fee fields; отсутствие поля не означает нулевую комиссию. Суммы аналитических категорий могут отличаться точностью представления от основной суммы; для Money требуется точная сумма операции.

## История, повторы и отказы

У текущего счёта было 20 строк истории; одно «Показать ещё» добавило ещё 20 и осталось доступным. Это наблюдение UI, без доказательства постоянного page size, cursor, полного покрытия или end marker. Выбранный в общей истории 01.08.2026–31.08.2026 показал августовские записи; все страницы диапазона не выгружались. Глубина хранения и включительность границ не установлены. Старые записи накопительного счёта показывают наличие истории, но не её непрерывность.

Повтор открытия одной выплаты процентов дал тот же текст диалога и тот же маршрут вклада. Возврат к текущему счёту из других разделов дал прежний URL. Это проверки внутри одной сессии; имитировать банковскую операцию для теста не требовалось. Чтение покупки при быстром закрытии/открытии не дало подтверждённой повторяемости и не считается успешным тестом. При двух timeout клика на «Выгода» и строку кэшбэка следующий snapshot показал уже выполненный переход; повторный клик не делался.

Ввод кода выполнил владелец после остановки на auth-origin. Данные «до» для проверки identity через этот вход не были собраны, поэтому reauth-стабильность не доказана. Второй внешний аккаунт участника семьи, session expiry, hourly run, поздние ревизии, refunds, resume после сетевой ошибки и отмена stale job после disconnect не проверены.
