## Access and secret boundary

BYBIT-E11 — **confirmed**: `GET /v5/user/query-api` returned `readOnly=1`, `isMaster=true`, a present `userID`, the requested IP restriction and exactly these nonempty permissions: `Wallet: [AccountTransfer]`, `Exchange: [ExchangeHistory]`, `Earn: [Earn]`, `FiatP2P: [FiatP2POrder]`. Trading, withdrawal and advertisement permissions were not enabled. This is the observed sufficient permission set, not proof that every permission is individually indispensable. The misleading `AccountTransfer` scope name does not authorize transfers: both the key and the future route allowlist must enforce read-only access.

[RSA signing](https://bybit-exchange.github.io/docs/v5/guide) uses SHA256/PKCS#1 v1.5 and base64 over timestamp + API key + receive window + the exact query string or POST JSON. The private key stays local; Bybit receives its public key. The owner entered MFA and saved the issued API key. Credential files have mode 0600; the private-key directory has mode 0700. The API key and local raw research responses are ignored by Git. No key, IP, UID, signature, raw response, payment detail or private credential location belongs in public documentation, Issues, AI input or application logs. The key-identity response itself echoes `apiKey` and must be filtered. Local ignored files are research material, not the production secret store or backup design.

The account accepted `https://api.bybit.com`. No paid API subscription was purchased. Chosen-VPS access, future expiry/rotation/revocation and a second owner's key were not exercised. API rejection must remain an access error, not trigger increased permissions or automatic browser fallback. No financial mutation was sent; the only POST reads were the two explicitly allowed P2P routes.
