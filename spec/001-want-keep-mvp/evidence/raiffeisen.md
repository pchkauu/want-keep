## Объём и выбранный путь

Владелец сообщил: используется расчётный счёт ИП в RBO для поступлений по контрактам; кредитов и вкладов нет. **Официальный API предпочтительнее Playwright.** Исследование и будущий импорт сначала используют API; браузерный сборщик рассматривается только при доказанном пробеле API. API-предпочтение не означает полный запрет резервного способа.

Google Chrome нужен владельцу для настройки интеграции и авторизации. Доступ агента к Chrome не является обязательной зависимостью исследования публичного API или последующего серверного импорта. Предыдущий просмотр страницы входа был в Arc, по уточнению владельца; он не доказывает истечение сессии в Chrome. Позже найден нужный Chrome-профиль и прочитан раздел интеграций (RAIF-E12); операции, реквизиты и остатки не исследовались.

D-35: владелец подтвердил только расчётный счёт ИП. Карты, кредиты, накопительные счета и вклады Raif исключены; другие провайдеры и общие функции сохраняются. REQ-043/AC-043 обновлены с сохранением ID.

## Подключение и авторизация API

Регистрация системы и первоначальный выпуск токена завершены владельцем в RBO; фактическая ротация и чтение — RAIF-E18–E24 ниже. Зарегистрирован https://want-keep.tech/api/v1/connections/raiffeisen/callback; DNS/HTTPS проверены, заглушка callback пока 503. Первичный токен из RBO позволил проверить API до реализации Code Flow приложения.

Будущий Code Flow по [контракту](../contracts.md) использует https://sso.rbo.raiffeisen.ru/authorize, точный redirect_uri, одноразовый code, state/nonce, PKCE S256 и привязки к владельцу/семье/версии подключения. Документированный scope — openid profile email phone; read-only банковский scope не доказан. Клиент независимо ограничивает запросы чтением. Платежи не выполнялись.

Обмен/refresh — POST https://sso.rbo.raiffeisen.ru/token. Для refresh: Basic Base64(client_id:client_secret), form-urlencoded grant_type=refresh_token, client_id, refresh_token. Code Flow дополнительно требует code, redirect_uri, code_verifier; он не запускался. Секреты/токены не выводятся.

Документация RAIF-E08 указывает access/id 24 часа и refresh 30 дней; оферта RAIF-E13 — refresh 180 дней. Ответ не содержит expires_in. Ротация проверена один раз; lifetime/logout/revocation/concurrent refresh, второй аккаунт и проверки OIDC остаются открыты. При unknown outcome повтор запрещён до сверки.

## Контракт счетов и выписок

| Операция | Подтверждённый контракт | Ограничение |
| --- | --- | --- |
| Список счетов | `GET https://api.openapi.raiffeisen.ru/api/v1/accounts?fields=Id,Number,Name,OrganizationName,Currency`; `Accept: application/json`, `Authorization: Bearer {access_token}`, `ID-Token: {id_token}`; HTTP 200, массив доступных пользователю счетов (RAIF-E09) | Проекция, типы и стабильность одного счёта проверены в RAIF-E19–E21; текущие остатки, пагинация и идентичность при reauth требуют проверки |
| Историческая/итоговая выписка | `POST https://api.raiffeisen.ru/bank-statements/v1/reports/camt-053`; JSON `accountKeys, from, to`; 202 с `reportId` (RAIF-E10) | `to` не может быть текущей датой; это ID задания, не ID операции |
| Выписка текущего дня | Тот же host/prefix, `POST /v1/reports/camt-052`; `from = to = текущая дата` | Банковская timezone и детализация внутридневных записей требуют проверки |
| Состояние задания | `GET /v1/reports/{reportId}/status`; 200, `reportId` и `status` | Enum: CREATED, STARTED, FAILED, STOPPED, RESTARTED, COMPLETED, CANCELLED. Это состояния генерации, не финансовой операции |
| Получение файла | `GET /v1/reports/{reportId}/file`, также HEAD для metadata; Range, ETag, Content-Length описаны | OpenAPI описывает binary/XML/ZIP и другие форматы, но не содержит XSD/структуру банковской операции |
| Проверка параметров | `dryRun=true` на POST генерации; 200 при успешной проверке без запуска задания | Не доказывает состав или полноту выписки; при false запускается генерация |

Все вызовы выписок требуют Authorization и Id-Token. У API счетов и выписок **разные опубликованные base URL**; нельзя переносить пути между ними автоматически. `accountKeys` содержит 20-значный номер счёта или `номер:CNUM`; равенство с `Id` из API счетов не предполагается. В RAIF-E20–E21 number без CNUM принят и совпал с номером в XML; применимость CNUM к другим аккаунтам требует проверки.

Синтетический пример по RAIF-E10; значения придуманы, запрос не выполнялся:

```http
POST /bank-statements/v1/reports/camt-053 HTTP/1.1
Host: api.raiffeisen.ru
Authorization: Bearer {access_token}
Id-Token: {id_token}
Content-Type: application/json

{"accountKeys":["00000000000000000000:123456"],"from":"2026-08-01","to":"2026-08-31","zero":true}

HTTP/1.1 202 Accepted
Content-Type: application/json

{"reportId":"00000000-0000-4000-8000-000000000001"}
```

```json
{"reportId":"00000000-0000-4000-8000-000000000001","status":"COMPLETED"}
```

Последний JSON — пример ответа status по документированной схеме. Только COMPLETED позволяет переходить к чтению файла; coverage считается подтверждённым после проверки содержимого. Генерация выписки создаёт отчёт, но не банковский платёж: POST входит в allowlist именно по этому назначению.

### История, ошибки и ограничения

- Для почасового импорта кандидат — camt.052 за текущий день; завершённые дни повторно сверяются по camt.053. RAIF-E04: итог за рабочий день доступен на следующий день после 04:00 МСК, рекомендуемый первый запрос — после 06:00; субботу запрашивать в понедельник либо в воскресенье после 14:00. Это не доказательство часовой актуальности самого источника.
- `zero=true` включает выписки без движений. Отсутствие выписки или 404 не означает нулевой баланс/полную историю. Точная включительность from/to, retention, максимальный период, число счетов/операций и квоты не описаны в проверенной спецификации.
- Описаны 400, 401, 404, 500; schema ErrorType использует UPPER_SNAKE_CASE, а JSON-примеры — kebab-case (`NO_STATEMENTS` / `no-statements`). Это конфликт документации. Реальные коды и соответствие проверить; неизвестная ошибка не продвигает coverage. Не классифицировать по свободному тексту message.
- Enum TOO_MANY_TRANSACTIONS_ERROR существует, числовой порог отсутствует. Дробление периода должно сохранять непроверенные интервалы. В CAMT-методах нет документированной пагинации операций: это отчёты, не постраничный transaction API.
- Нет описанного idempotency key генерации. Повторное задание после timeout не должно повторно проводить деньги. Восстановление использует известный reportId; после получения файла дедупликация требует устойчивого ID операции. Report ID или file hash не заменяют такой ID.
- Range/If-None-Match присутствуют, но ответы 206/304 не перечислены. Возобновление скачивания по диапазонам пока не считается подтверждённым. Срок хранения готового файла, polling interval и статус STOPPED/RESTARTED требуют проверки.

## Production-прогон и mapping, 2026-09-07

Исследование завершено с документированными блокерами по правилу README. После выпуска владельцем Refresh-токена выполнен refresh grant: HTTP 200, новый комплект атомарно сохранён с mode 0600 в локальном каталоге 0700, Refresh-токен изменился. Basic Base64 подтверждён; ответ содержит access_token/id_token/refresh_token/token_type, без expires_in. Исходный файл — bootstrap, последующие команды используют tokens.json. Скрипты не выводят credentials. JWT используется как непрозрачный API credential из TLS-ответа банка; это не проверка OIDC-входа приложения.

Два GET счетов с Mac вернули один и тот же счёт. После отдельного разрешения владельца выполнен один GET с VPS в Германии: HTTP 200, те же id/number. Access/id токены переданы по SSH в память процесса; скрипт не пишет их на VPS. Ответ хранится приватно на Mac. Постоянные credentials на сервер не установлены; refresh и выписки с VPS не проверялись.

Для 2026-08-01–2026-08-31: dryRun 200 → generation 202 → status 200 completed → file 200. Независимый отчёт за 2026-08-01–2026-08-30 прошёл 202 → completed → 200. Получены XML camt.053.001.08, по семь BOOK-записей: два CRDT и пять DBIT. NtryRef и сами Ntry побайтово совпали между отчётами. По Decimal начальный остаток OPBD + движения = конечный CLBD; суммы/направления вложенных TxDtls совпадают с Ntry.

Запрос camt.052 за 2026-09-07 вернул 404 с {"code":"no-statements"}. Это не нулевой остаток и не доказательство полной истории. Текущий/intraday остаток не подтверждён. Фактические completed/no-statements отличаются от OpenAPI COMPLETED/NO_STATEMENTS; преобразование явно учитывает только известные значения, исходные данные сохраняются.

| Источник | Наблюдение и правило |
| --- | --- |
| accounts | lower-camel-case id/number/name/organizationName/currency — строки. id имеет форму UUID и отличается от number из 20 цифр. Повторный GET стабилен |
| accountKeys | number принят в запросе выписки и совпал с Stmt/Acct/Id/Othr/Id; UUID id не подставлять вместо номера |
| Валюта | JSON RUR, XML RUB: явный алиас RUR→RUB с сохранением исходного значения |
| Stmt/Bal | OPBD/CLBD содержат Amt, CdtDbtInd, Dt/DtTm. Это исторические остатки; available/locked не подтверждены |
| NtryRef | Семь непустых уникальных значений на двух отчётах; кандидат dedup key внутри устойчивого счёта. Reconnect/коррекции/другие аккаунты ещё не проверены |
| AcctSvcrRef / EndToEndId | AcctSvcrRef есть только у двух записей; EndToEndId уникален у семи. Их нельзя считать обязательным универсальным ключом |
| NtryDtls/TxDtls | По одной вложенной записи на наблюдаемую Ntry; не проводить деньги второй раз. Общий 1:N контракт не проверен |
| Даты | BookgDt/ValDt имеют offset; диапазон 00:00:00–23:59:59 с +03:00. Другие TZ/статусы не проверены |
| BkTxCd/Prtry/Cd | NTRF у шести записей, FCHG у одной DBIT. Это proprietary codes; семантика комиссии и внутренних переводов отдельно подтверждается |
| RltdPties/RltdAgts/RmtInf | Стороны, реквизиты и два Ustrd на запись; недоверенное описание/происхождение, не команды и не замена ID |

[JSON](raiffeisen.samples.json) и [XML](raiffeisen.camt053.sample.xml) используют только синтетические значения. XML иллюстрирует наблюдаемую структуру; полная XSD-валидация не заявляется. Код NTRF не доказывает внутрисемейный перевод; перевод с ИП на свой личный счёт не создаёт новый семейный доход.

## Матрица продуктов и блокеры

По прямому решению владельца D-35 обязательный Raif-продукт — только расчётный счёт ИП: остатки, поступления, списания, комиссии и история через API. Карты, кредиты, накопительные счета и вклады Raif исключены из текущего MVP; остальные платформы и общие функции сохранены. Курсы buy/sell не получены и не выдумываются.

| ID | Состояние | Доказательство / оставшийся вопрос |
| --- | --- | --- |
| RAIF-B01 | Закрыт для первичного API-доступа | Refresh и account GET с Mac, account GET с VPS — HTTP 200; это не постоянная интеграция |
| RAIF-B02 | Частично закрыт: accounts/CAMT mapping | Нужны XSD, 1:N, reversal/pending и ID при исправлениях. Профиль проверен на двух отчётах |
| RAIF-B03 | Открыт: полнота/история | Архив/retention/квоты, пустые дни, split/resume, поздние изменения и camt.052↔053 replay |
| RAIF-B04 | Открыт: авторизация/эксплуатация | Refresh 30/180 дней, reauth/revocation, второй внешний аккаунт, постоянное защищённое хранение, hourly import; callback пока 503 |
| RAIF-B05 | Закрыт | D-35 заменяет исходный retail scope только расчётным счётом ИП |
| RAIF-B06 | Открыт в новом scope | Текущий/доступный/заблокированный остаток и точная семантика комиссии. 404 не равен нулю; неиспользуемые продукты не блокируют |

Следующие проверки: успешный intraday в доступный банковский день, источник текущего остатка при no-statements, bank semantics комиссий, глубина истории, reauth и второй аккаунт. Деньги ради тестов не перемещать; refresh/генерацию после unknown outcome не повторять без сверки. task-0.10 закрывает оставшиеся вопросы; task-4.2 и весь MVP остаются Not Ready.
